How It Works — Deep Dive

System Architecture

Municode splits responsibility cleanly across an API, a background Worker, and an edge Gateway—isolating public browser traffic from cloud credentials, database state, and VM management tunnels.

1. Control-plane components & network boundaries

Inside the control plane, services communicate across segmented private networks so the public-facing Gateway never holds database or cloud-provider secrets:

  • Reverse Proxy & Web Console: Terminates HTTPS for the console, API, and wildcard workspace origins, requesting on-demand certificates only for active, authorized workspace routes.
  • Workspaces Gateway: Validates browser launch codes and session cookies, re-verifies active WebSocket streams, and forwards authorized traffic onto an internal relay network.
  • Workspaces API: Owns organizations, user roles, admitted VM images and plans, workspace lifecycle state, and short-lived Git access tokens.
  • Workspaces Worker: Reconciles cloud VMs and volumes via provider adapters, verifies per-generation VM host keys, and maintains the private SSH tunnels that feed the Gateway.

2. Generation-bound VM enrollment & session launch

Every time a workspace VM starts, Municode increments its generation counter. Host keys, volume mounts, launch links, and active browser sockets are all bound to that exact generation:

  1. VM bootstrap & enrollment: After booting a VM from your selected image, the Worker configures the guest over a pinned tunnel and supplies a one-time enrollment token. The VM verifies its workspace mount and local services, then posts an enrollment receipt to the API before routes open.
  2. Single-use launch links: Opening a workspace IDE or preview calls the API to mint a generation-bound URL with a single-use code.
  3. Isolated origin cookies & live revocation: The Gateway exchanges the code for a host-only cookie on that service's dedicated subdomain, injects session credentials server-side over the private tunnel, and closes WebSockets immediately if access is revoked or the VM stops.

3. Storage tiers & ephemeral Git VMs

Municode supports two complementary VM modes inside a workspace, and keeps durable project state separate from disposable caches:

  • Persistent Volume (Primary VMs): Holds your repositories, IDE threads, home configuration, and workspace files. Ownership and volume identity are verified before mounting, and old VM compute is proven absent before reattaching to a new VM generation.
  • Local Scratch Disk: Package caches, temporary files, and heavy build outputs stay on the VM's fast local disk rather than bloating your persistent volume, and rebuild cleanly when a VM is replaced.
  • Ephemeral Git VMs: Boot with no persistent volume attached, clone an authorized repository and commit onto a dedicated branch using short-lived repository-scoped credentials, and verify that commits are pushed before shutting down.

4. Navigating the repository

  • src/Workspaces.Api — Authentication, organization RBAC, image/plan admission, and workspace lifecycle API.
  • src/Workspaces.Worker — Cloud VM/volume reconciliation, guest bootstrap, and private tunnel management.
  • src/Workspaces.Gateway — Launch-code redemption, origin isolation, and HTTP/WebSocket session relay.
  • src/Workspaces.Cli — Standalone municode / workspaces CLI and seed bootstrap workflow.
  • modules/dashboard — Web console frontend.
  • templates/development-workspaces — Reference guest runtime scripts and image builder template.
