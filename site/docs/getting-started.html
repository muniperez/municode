Setup Guide

Deploying a Municode Control Plane

Municode deploys as a self-contained control plane. You can provision a fresh host automatically with workspaces seed or install the release bundle onto an existing server with Docker Compose.

1. Bootstrap a control plane with workspaces seed

workspaces seed (or municode seed) provisions a single control-plane host from a signed release. It quotes recurring costs before creating any resources, records every step in a local journal so interrupted runs resume cleanly, and pauses for out-of-band SSH host verification and DNS setup.

Safety guarantees: Seed creates no coding VMs, requires explicit cost-digest approval before provisioning, and reads your bootstrap cloud token only from a local file—never copying it onto the control-plane server.

Commands

shell 
# 1. Store your cloud API token in a protected local file
install -m 600 /dev/null /protected/provider.token

# 2. Verify release signature & quote recurring host cost
workspaces seed plan \
  --provider <provider> --region <region> --size <size> \
  --dashboard-hostname console.example.com \
  --api-hostname api.example.com \
  --gateway-domain workspaces.example.com \
  --release workspaces-vX.Y.Z \
  --credential-file /protected/provider.token

# 3. Provision the control-plane host with the approved plan digest
workspaces seed apply <operation> \
  --credential-file /protected/provider.token \
  --approve <approval-digest>

# 4. Read the host's ed25519 SSH fingerprint from your provider console,
#    point the 3 DNS records below at the host IP, and resume:
workspaces seed resume <operation> \
  --credential-file /protected/provider.token \
  --confirm-console-fingerprint SHA256:...

Required DNS records

Public DNS records pointing to your control-plane host
Record Type Target Purpose
console.example.com A Control-plane public IPv4 Web console UI
api.example.com A Control-plane public IPv4 Control-plane API & CLI endpoint
*.workspaces.example.com A Control-plane public IPv4 Isolated origins for workspace IDE & preview sessions

2. Manual installation on an existing host

If you already run your own server with Docker Engine and Compose v2, extract a verified release archive and run the installer directly:

shell 
sha256sum --check --strict checksums.txt
tar -xzf municode-workspaces-X.Y.Z-linux-any.tar.gz
cd municode-workspaces-X.Y.Z
./install.sh --install-root /opt/municode/workspaces \
  --secrets-dir /etc/municode/workspaces/secrets

# Configure hostnames in /opt/municode/workspaces/.env, initialize secret storage,
# run migrations, and bring up the stack:
cd /opt/municode/workspaces
docker compose up -d postgres openbao
OPENBAO_ROOT_TOKEN_FILE=/protected/root-token \
  docker compose --profile maintenance run --rm openbao-configure
docker compose up database-initialize kratos-migrate api-migrate
docker compose up -d

See the Operator Guide for full OpenBao initialization, offline recovery custody, first-owner bootstrap token generation, and upgrade steps.

3. Register your cloud account, VM images & plans

After signing in as the first organization owner, configure what developers can launch:

  1. Register a cloud provider account in the console or API—credentials are stored encrypted in the control plane's secret store.
  2. Register one or more VM images with the operating system, SDKs, and coding agents your team wants. You control the image contents and rollout lifecycle; the repository also includes a reference image template under templates/development-workspaces.
  3. Admit compute plans (regions, VM sizes, and cost estimates) so engineers can select them from the web console or CLI.
